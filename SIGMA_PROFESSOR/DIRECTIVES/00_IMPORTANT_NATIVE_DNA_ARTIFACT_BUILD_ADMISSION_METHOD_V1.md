# IMPORTANT — NATIVE DNA ARTIFACT BUILD & ADMISSION METHOD V1

Status: **MANDATORY METHOD NOTE FOR FUTURE SIGMA WINDOWS / AGENTS**

Purpose: preserve the proven SIGMA build/admission method so future windows do not replace native SIGMA cognition with host logic, rebuild admitted artifacts without evidence, weaken tests to force PASS, or overclaim beyond exact runtime evidence.

This note is a **method flag**. DNA-specific workflows may add stricter gates, but they must not silently weaken the native/host ownership boundary below.

---

## 1. PRIMARY OWNERSHIP RULE

SIGMA native code must own the cognition, derivation, state transition, decision, ranking, learning update, or other capability that the DNA claims to prove.

The host may only provide mechanical execution/support required by the architecture and harness.

Required pattern:

```text
exact admitted dependencies
-> locked compiler / locked SIGMA VM
-> compile native .sigma source
-> freeze source + generated bytecode identity
-> generate runtime/dynamic inputs after compile where required
-> run native VM
-> capture raw VM stdout/stderr
-> start post-VM test oracle
-> independent alignment / adversarial checks
-> verify source/bytecode unchanged
-> aggregate hard gates
-> ADMISSION decision
```

Forbidden inversion:

```text
host understands/computes/selects
-> host writes semantic answer/state
-> SIGMA merely echoes it
```

If the host must compute a SIGMA decision for the gate to pass, the native gate fails.

---

## 2. DO NOT REBUILD ADMITTED ARTIFACTS WITHOUT DAMAGE EVIDENCE

If a prior DNA/support stage is already admitted in exact tested scope:

- reuse the exact bundle/source/runner/checkpoint when available;
- verify exact identities by hash;
- do not reconstruct ABI from chat summaries while exact bytes are accessible;
- do not reopen an already-PASS stage merely because a new window cannot immediately see the old artifact;
- reopen only for concrete corruption, dependency breakage, incompatible ABI, or a genuinely new unproven scope.

Historical PASS remains historical evidence. New scope requires new evidence; it does not justify rewriting the old result.

---

## 3. LOCK DEPENDENCIES BEFORE ACTIVE BUILD

Before compiling the active DNA, verify every material dependency used by that DNA.

Where applicable, equality-gate exact values such as:

```text
DEPENDENCY_ADMISSION=PASS
DEPENDENCY_RESULT=PASS_IN_EXACT_TESTED_SCOPE
DEPENDENCY_SOURCE_SHA256=<locked>
DEPENDENCY_BYTECODE_SHA256=<locked>
HOST_SEMANTIC_SUBSTITUTION=NO
PYTHON_USED=NO              # only when the exact workflow requires it
```

Do not trust dependency identity only by directory name, filename, comments, or human description.

Mismatch => **FAIL CLOSED**.

---

## 4. COMPILE ONCE, THEN FREEZE SOURCE/BYTECODE IDENTITY

Preferred ordering:

```text
1. verify locked compiler / VM / prerequisite artifacts
2. verify active source / runner / manifest identities
3. compile active .sigma source
4. hash and freeze source + generated bytecode
5. only then create dynamic runtime fixtures
6. execute the bounded suite against that frozen artifact
7. re-hash source + bytecode after all runs
```

Required evidence where applicable:

```text
SOURCE_UNCHANGED_AFTER_DYNAMIC_TEST=YES
BYTECODE_UNCHANGED_AFTER_DYNAMIC_TEST=YES
```

Do not modify source/bytecode between cases and aggregate those runs as one admission.

If active source changes, it is a new candidate artifact and the affected scope must be re-tested.

---

## 5. DYNAMIC INPUT MUST NOT BE A COMPILE-TIME FIXTURE

For anti-hardcode / dynamic-binding evidence, generate runtime values **after compile/bytecode freeze**.

Where relevant, expose:

```text
DYNAMIC_INPUT_PRESENT_AT_COMPILE_TIME=NO
DYNAMIC_INPUT=YES
```

Use unseen/high-entropy tokens when the claim requires proof of dynamic binding.

After the suite, verify:

```text
UNSEEN_HIGH_ENTROPY_TOKEN_LEAK_COUNT_IN_SOURCE_OR_BYTECODE=0
```

A value generated after compilation and then handled correctly by native runtime is stronger evidence than a fixed token embedded in source.

---

## 6. NATIVE VM MUST PRODUCE THE CLAIMED RESULT

If a DNA claims computation, classification, derived parameter, decision, persistent update, tool demand, ranking, strategy update, or learning behavior, the claimed value must be materially produced by SIGMA native execution.

Reference pattern proven by DNA-15:

```text
observation
-> native ratio
-> native log
-> native parameter derivation
-> native exp/reconstruction
-> native VM output
```

The host must not calculate the target result first and feed it back as if SIGMA derived it.

For tool/learning lanes, preserve relevant ownership flags, for example:

```text
HOST_LEARNING=NO
HOST_WEIGHT_UPDATE=NO
HOST_STRATEGY_UPDATE=NO
HOST_SCOPE_INFERENCE=NO
HOST_DEMAND_GENERATION=NO
HOST_TOOL_SELECTION=NO
HOST_TOOL_RANKING=NO
HOST_SEMANTIC_SUBSTITUTION=NO
```

Only claim the fields actually proven by the DNA under test.

---

## 7. POST-VM ORACLE STARTS AFTER NATIVE EXECUTION

Independent expected-value calculation is allowed as a **test oracle after the VM run**.

Preferred ordering/evidence:

```text
run SIGMA VM
-> capture exact raw stdout/stderr
-> VM execution ends
-> CASE_xxx_POST_VM_TEST_ORACLE_STARTED=YES
-> calculate independent expected result
-> compare expected vs native actual
```

The oracle may validate correctness. It must not become the producer of SIGMA's semantic output.

A Bash/awk/Python calculation used only after VM execution is harness logic, not native cognition, and must never be described as SIGMA learning/reasoning. If a stage requires `PYTHON_USED=NO`, honor that exact gate.

---

## 8. PRESERVE RAW VM EVIDENCE BEFORE HOST INTERPRETATION

For each case, preserve exact machine evidence where practical:

```text
CASE_xxx_LABEL=<label>
CASE_xxx_INPUT_SHA256=<hash>
CASE_xxx_VM_RC=<rc>
CASE_xxx_VM_STDOUT_SHA256=<hash>
CASE_xxx_VM_STDERR_SHA256=<hash>
CASE_xxx_SENTINEL_PRESENT=<0|1>
--- RAW SIGMA VM CASE xxx STDOUT ---
<exact native stdout>
--- RAW SIGMA VM CASE xxx STDERR ---
<exact native stderr>
CASE_xxx_POST_VM_TEST_ORACLE_STARTED=YES
CASE_xxx_POST_VM_ALIGNMENT=<YES|NO>
```

Do not hide a failing native output behind a transformed host summary.

If parsing is required, mechanically parse exact field/value bytes. Do not rewrite scope, demand, state, candidate, truth status, or semantic meaning to make a downstream gate pass.

---

## 9. TEST THE CLAIM WITH MULTIPLE EVIDENCE CLASSES

Exact cases are DNA-specific, but strong admission should use the evidence classes required to falsify the claim, such as:

- normal valid cases;
- boundary/state-partition cases;
- malformed/incoherent refusal cases;
- dynamic unseen tokens;
- byte-identical replay;
- stale-input independence when removing an old active dependency;
- reorder invariance when order must not affect semantics;
- availability/readiness/cost/prior-use causal changes when claimed;
- learning counterfactual with/without experience;
- unknown candidate / tool-gap HOLD behavior;
- demand mismatch proving demand is not rewritten to fit a tool.

Do not add cosmetic cases merely to reach a desired count.

---

## 10. REPLAY AND STALE-INPUT INDEPENDENCE ARE DIFFERENT

Replay asks whether identical complete input/prestate gives identical native result:

```text
REPLAY_IDENTICAL_INPUT_DECISION=YES
```

Stale-input independence asks whether a removed old input can change externally without controlling the active result:

```text
stale external value changes
-> raw input/hash reflects change where applicable
-> native output stays invariant
```

This runtime independence evidence is stronger than source-text inspection alone.

Do not confuse the two tests.

---

## 11. LEARNING CLAIMS REQUIRE CAUSAL COUNTERFACTUAL EVIDENCE

Logging experience is not self-learning.

A learning DNA must establish a causal chain such as:

```text
experience E1
-> SIGMA native persistent state changes
-> fresh VM reads learned state
-> same/similar context is evaluated
-> future decision/weight/strategy changes because of E1
```

Also require a counterfactual:

```text
without E1 -> old decision/state
with E1    -> changed decision/state
```

If weights are changed, prefer native evidence such as:

```text
WEIGHT_BEFORE
OBSERVED_RESULT
NATIVE_UPDATE_REASON
WEIGHT_AFTER
```

while preserving:

```text
HOST_LEARNING=NO
HOST_WEIGHT_UPDATE=NO
HOST_STRATEGY_UPDATE=NO
HOST_SEMANTIC_SUBSTITUTION=NO
```

Do not call host-side scoring, logging, or replayed host policy "self-learning".

---

## 12. TOOL AUTONOMY REQUIRES STRICT NATIVE/HOST SEPARATION

Target ownership chain:

```text
SIGMA native cognition
-> recognize need for capability/tool
-> native capability demand/scope
-> native weighted arbitration
-> native selection/composition
-> host mechanical execution/transport only
-> exact result/provenance returned
-> SIGMA native evaluation
-> persistent experience
-> SIGMA native learning/update
-> next native decision
```

Host/supervisor may own:

```text
process launch
network transport
filesystem transport
exact protocol decode
resource/timeout enforcement
crash restart
logging
```

SIGMA must own, when claimed:

```text
what to do
whether a tool is needed
which capability scope is needed
which tool/capability to select
whether evidence is sufficient
whether to continue
whether/how to learn/update
next action
```

A Bash/Python daemon must never become an external AI making these decisions for SIGMA.

---

## 13. FAIL LOCAL, FIX MINIMALLY, RERUN THE FULL REQUIRED SUITE

When a case fails, do not rewrite the whole DNA or weaken the gate first.

Classify the defect:

```text
A. native source/policy defect
B. runner/harness defect
C. post-VM oracle defect
D. compiler/VM ABI defect
E. dependency identity mismatch
F. claim broader than implemented behavior
```

Change only the layer proven wrong.

Historical failure evidence should remain available when useful; do not erase it merely because FIX1/FIX2 later passes.

After any fix, rerun the **entire required admission suite**, not only the previously failing cases.

A two-case repair does not authorize a two-case admission when the workflow requires 50 cases.

---

## 14. ADMISSION MUST BE MACHINE-GATED

Admission is not a human impression.

Typical aggregate hard gates, where applicable:

```text
TOTAL_VM_INVOCATIONS=<required>
POST_VM_ALIGNMENT_PASS_COUNT=<all required>
POST_VM_ALIGNMENT_FAIL_COUNT=0
POST_VM_NUMERIC_ALIGNMENT_PASS_COUNT=<all required numeric cases>
POST_VM_NUMERIC_ALIGNMENT_FAIL_COUNT=0
VM_NONZERO_COUNT=0
STEP_LIMIT_HIT_COUNT=0
SENTINEL_FAIL_COUNT=0
SOURCE_UNCHANGED_AFTER_DYNAMIC_TEST=YES
BYTECODE_UNCHANGED_AFTER_DYNAMIC_TEST=YES
UNSEEN_HIGH_ENTROPY_TOKEN_LEAK_COUNT_IN_SOURCE_OR_BYTECODE=0
REPLAY_IDENTICAL_INPUT_DECISION=YES       # when required
ADMISSION=PASS
RESULT=PASS_IN_EXACT_TESTED_SCOPE
```

DNA-specific causal gates must be added where needed.

Partial evidence must remain explicitly partial:

```text
CASE_05_TO_12=PASS
FULL_ADMISSION=NOT_YET_PROVEN
```

Never upgrade partial PASS to full admission by narration.

## 15. CLAIM SCOPE MUST NOT EXCEED EXECUTED EVIDENCE

The final claim must state exactly what runtime proved and what remains unproven/not executed.

Preserve explicit boundaries where relevant, e.g.:

```text
K_TEMPORAL_CONSTANCY=NOT_PROVEN
DERIVATIVE_FROM_DERIVED_K=NOT_EXECUTED
PARAMETER_OPTIMIZATION=NOT_EXECUTED
CAPABILITY_GROWTH=NOT_EXECUTED
MODEL_REPLACEMENT=NOT_EXECUTED
LEARNING_RUNTIME=NOT_EXECUTED
```

DNA-15 is a canonical warning: it proves native interval-derived parameter behavior and reconstruction in exact tested scope. It does **not** by itself prove long-term growth constancy, out-of-sample prediction, general self-learning, or capability growth.

Use semantically bounded names such as:

```text
INTERVAL_DERIVED_K
```

instead of unsupported stronger labels.

---

## 16. BUNDLE / MANIFEST DISCIPLINE

Do not assume every bundle must contain prebuilt bytecode.

A valid admission packaging pattern may be:

```text
bundle:
- exact .sigma source
- exact runner
- MANIFEST.sha256
- locked references/dependency records

runtime:
- verify manifest
- compile with locked compiler
- hash/freeze generated bytecode
- run full suite against frozen artifact
```

Inspect the exact workflow before assuming which files belong in a bundle.

Do not reconstruct a missing artifact merely because a previous DNA used a different packaging pattern.

---

## 17. REQUIRED PRE-BUILD QUESTIONS FOR A NEW DNA

Before authoring/changing a DNA, answer these from exact artifacts/workflow:

```text
1. What exact native capability is this DNA supposed to prove?
2. Which admitted dependencies are required?
3. What exact input/state ABI reaches the VM?
4. What exact fields/files does native SIGMA produce?
5. Which result must be native, and which host actions are purely mechanical?
6. What adversarial/counterfactual test would falsify the claim?
7. What replay/invariance behavior is expected?
8. Which source/bytecode identities must remain unchanged?
9. What exact hard gates determine PASS?
10. What tempting stronger claim must remain NOT_PROVEN/NOT_EXECUTED?
```

If these cannot be answered from exact source/runner/workflow, inspect those artifacts first. Do not invent ABI from memory or chat summaries.
